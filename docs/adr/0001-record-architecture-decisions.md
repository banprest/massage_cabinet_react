# 0001. Ведём ADR

- Статус: Принято
- Дата: 2026-10-05

## Контекст
Я один пишу этот проект, без нормированного графика. Этот проект пойдёт в портфолио и также будет сайтом для моего друга.

## Решение
Для понимания контекста принятых решений мы будем писать adr. Мы введём adr по следующим правилам.
- храним в docs/adr
- нумерация от 0001 по правилу новый документ +1 к предыдущему номеру
- есть статусы Предложено / Принято / Отменено / Заменено ADR-XXXX
- есть одно общее тело для всех adr
- главное правило: принятый ADR не редактируют, а заменяют новым.

## Рассмотренные альтернативы
### Вариант A
Не делать ADR
Плюсы
- Мы не тратим на это время
Минусы
- В процессе разработки мы можем забыть какие решения и зачем были приняты
### Вариант B
Документировать код
Плюсы
- Все методы и классы будут задокументированы и мы по коду поймём что и зачем было сделано
Минусы
- Много мусора
- Не покажет вариант, который мы не выбрали
### Вариант C
Использовать PR
Плюсы
- Каждый PR задокументирован
- Не надо создавать доп документы
Минусы
- Нет выделенного контекста и разделения на архитектурные и обычные решения.


## Последствия
Станет проще понимать, что и зачем было сделано в процессе разработки и какие решения принимались для этого.
По минусам на писании adr тратит время пару часов на написании и осмысление написанного,
если я забуду написать adr то может так случится, что я буду гадать, что и зачем было сделано.
