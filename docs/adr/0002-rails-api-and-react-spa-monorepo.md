# 0002. Rails API и React SPA в монорепозитории

- Статус: Принято
- Дата: 2026-10-05

## Контекст
Это проект для портфолио, который я решил сделать для своего друга. Он не полностью учебный
это реальный проект, которым будут пользоваться люди, в проекте будет личный кабинет клиента, админка мастера,
возможность записи. Моя цель научиться работать с REACT, чтобы использовать его в работе

## Решение
Мы используем Ruby on Rails + React, бд Postgresql, API + SPA в одном репозитории

## Рассмотренные альтернативы
### Вариант A
Rails + Turbo
Плюсы:
- Быстрая разработка, так как работал с этими инструментами
- Лёгкая поддержка и настройка
Минусы:
- Не многому научусь. Не особо интересно снова плодить проект, который уже несколько раз делал
### Вариант B
Rails + чистый Javascript
Плюсы:
- Быстрая разработка
Минусы
- Сложная поддержка фронта для меня, не знаю паттернов и думаю утону в костылях
### Вариант C
Rails + Inertia + React
Плюсы:
- Api не требуется
- Аутентификация как в Rails, работает из коробки
- SEO легче чем в нашем варианте
- Легче и быстрее разрабатывать
Минусы:
- Тяжелее масштабироваться под мобилку
- Нишевый продукт для моего стека
### Вариант D
Два репозитория
Плюсы:
- логика разграничена
Минусы:
- Сложнее связать их и деплоить

## Последствия
- Авторизации через обычное приложение Rails работает из коробки,
- В нашей реализации такого нет и мы будем использовать cookie, а не jwt токен и из-за этого возникнут сложности в реализации.
- Между фронтом и бэком появляется граница, которую нужно явно поддерживать: контракт, генерация типов, проверка в CI. Позже добавится версионирование API (/api/v1) для изменений, которые ломают совместимость.
- Вдвое больше настройки, обновлений зависимостей и мест, где что-то может сломаться. Для одного разработчика это заметная нагрузка.
- У SPA есть известная проблема с SEO и превью ссылок, публичные страницы потребуют отдельного решения.
- В планах Telegram Mini App и, возможно, мобильное приложение, им нужен тот же бэкенд.
- Один бэкенд для всех клиентов — главный аргумент «за», ради которого мы платим цену прошлых пунктов.
